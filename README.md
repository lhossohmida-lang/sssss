# نظام إدارة مدرسة دروس خصوصية

ثلاثة تطبيقات Flutter في مستودع واحد (monorepo)، بواجهة عربية كاملة من اليمين إلى
اليسار والعملة دج، تعمل **محلياً أولاً**: كل كتابة تُحفظ على الجهاز ثم تُزامَن مع
خادم Supabase حين يتوفر الاتصال.

| المسار | المحتوى |
| --- | --- |
| `apps/admin` | تطبيق الإدارة (Android + Windows): التلاميذ والأفواج والحضور والمدفوعات والأساتذة والعمال والرسائل والتقارير والمساعد |
| `apps/teacher` | تطبيق الأستاذ (Android): حصصه وحضورها والطلبات والخلاص والنتائج والملفات |
| `apps/student` | تطبيق الوليّ والتلميذ (Android): الأبناء وحضورهم وجدولهم ومدفوعاتهم ونتائجهم ورمز الدخول |
| `packages/core` | القاعدة المحلية (drift)، الخدمات وقواعد الحساب، المزامنة، المصادقة |
| `packages/ui` | نظام التصميم claymorphism والهيكل المشترك والشاشات المشتركة |
| `packages/chat` | المحادثات |
| `packages/sms` | طابور الرسائل القصيرة وعامل الإرسال |
| `packages/assistant` | المساعد الذكي (عميل النموذج والأدوات المقيَّدة بالدور) |
| `supabase/` | مخطط الخادم وقواعد الصلاحيات والتخزين ودالة المساعد واختبارات SQL |

## 1. المتطلبات

- **Flutter 3.47.9** (القناة المستقرة؛ هذا هو الإصدار المثبَّت في مسارات البناء).
- **Android**: Android SDK وJDK 17 لبناء ملفات APK.
- **Windows** (نسخة الإدارة): Visual Studio مع حِمل «Desktop development with C++».
- على Linux أو macOS يثبّت `source tool/setup_env.sh` Flutter ويجلب الحزم؛ على Windows ثبّت
  Flutter يدوياً ثم نفّذ `flutter pub get` من جذر المشروع.

## 2. التشغيل للمطوّر

```bash
flutter pub get
dart format .                                      # التنسيق
flutter analyze --fatal-infos --fatal-warnings     # التحليل: صفر ملاحظات
dart run melos run test --no-select                # كل اختبارات الحزم
```

على حاسوب بطيء قد يُفسد التوازي زمن الاختبارات؛ شغّل الحزم بالتتابع:

```bash
dart run melos exec --concurrency=1 --dir-exists=test -- "flutter test"
```

تشغيل تطبيق: `cd apps/admin && flutter run -d windows` (أو `-d <جهاز Android>`)، وكذلك
`apps/teacher` و`apps/student`.

## 3. الوضع المحلي والاتصال بالخادم

يتصل كل تطبيق بخادم مدرسته بإحدى طريقتين:

1. **وقت التشغيل (الأصل):** النسخة العامة لا تضمّن خادم مدرسة. مع **دليل المدارس** (`OPERATIONS.md` القسم 12) يدخل صاحب المدرسة والعمال
   برقم الهاتف وكلمة السر فيعرف التطبيق المدرسة وحده، ويختار الأستاذ والوليّ مدرستهما من قائمة. دون دليل (بناء تطوير) يُلصق «رمز المدرسة»
   `SCH1.…` أو يُمسح بالكاميرا (القسم 9). ملف واحد يخدم كل المدارس.
2. **وقت البناء (بناء خاص بمدرسة):** يُمرَّر بـ`--dart-define` ولا يُحفظ شيء منه في المستودع (وهو عام):

```bash
flutter build apk --release \
  --dart-define=SUPABASE_URL=https://<مشروعك>.supabase.co \
  --dart-define=SUPABASE_ANON_KEY=<المفتاح العام anon/publishable>
```

المفتاح العام مصمَّم ليُضمَّن في التطبيقات؛ صلاحيات البيانات يحميها RLS على الخادم لا سرّيته. **دون خادم**
(لا ربط ولا إعداد بناء) يعمل تطبيق الإدارة وحده في «المعاينة المحلية»: لا خادم ولا مزامنة، وتُنشأ القاعدة
على الجهاز ويُنشأ حساب صاحب المدرسة عند أول تشغيل؛ أما تطبيقا الأستاذ والوليّ فيطلبان الربط. لا تضع مفتاح
`service_role` ولا أي مفتاح سرّي في التطبيق أو المستودع.

## 4. إعداد Supabase

ملفات الخادم في `supabase/migrations` وتُطبَّق **بهذا الترتيب** على مشروع جديد (من
محرر SQL في لوحة Supabase أو `supabase db push`):

| الملف | المحتوى |
| --- | --- |
| `0001_schema.sql` | الجداول والفهارس ومحفِّزات ختم المزامنة (مولَّد من مخطط drift) |
| `0002_rls.sql` | صلاحيات الصفوف لكل دور (صاحب المدرسة، العامل بصلاحياته، الأستاذ، الوليّ) والعروض المحجوبة `teacher_cards` و`group_cards` |
| `0003_storage.sql` | مخزنا الملفات `photos` (يكتبها الموظفون) و`files` (ملفات الأفواج والمرفقات) |
| `0004_chat_contact_accounts.sql` | حسابات جهات الاتصال للمحادثات |
| `0005_push_installations.sql` | تثبيتات إشعارات الدفع |
| `0006_photo_upload_limit.sql` | حد حجم الصور |
| `0007_push_sender.sql` | مشغّلا إرسال الدفع (pg_net) على الإشعارات ورسائل المحادثة، وجدول إعداد مغلق ودالة `set_push_config` |

بعد تغيير جداول drift: `dart run build_runner build` داخل `packages/core`، ثم أعد توليد
مخطط الخادم: `UPDATE_SCHEMA=1 flutter test test/data/supabase_schema_test.dart`
(في PowerShell: `$env:UPDATE_SCHEMA=1` قبل الأمر) وأضف الملفات المولَّدة.

اختبارات الخادم تعمل على PostgreSQL 16 معزول:

```bash
tool/pg_test.sh        # يحتاج PostgreSQL 16 وbash؛ مهمة server-sql في Actions تشغّلها عند كل push
```

> **النشر الآلي:** مسار `supabase-deploy` يطبّق الترحيلات ويرفع الدوال ويهيّئ المدرسة (تعطيل التسجيل
> العام وإنشاء حساب المالك)، ويشغّل فحوص العقد على مدرسة العرض. خطوات مدرسة جديدة وكلفتها في
> **`OPERATIONS.md`**.

## 5. المساعد الذكي (دالة الخادم)

المساعد يمرّ عبر دالة Supabase Edge في `supabase/functions/assistant`: التطبيق يرسل
الطلب بجلسة المستخدم، والدالة تتحقق من دوره وتتصل بنموذج لغوي عبر واجهة **متوافقة مع
OpenAI** (OpenRouter افتراضياً). **مفتاح النموذج لا يُضمَّن في أي تطبيق** بل يُحفظ سرّاً
على الخادم، ولكل مدرسة مفتاحها (ويفضَّل أن يكون بحد إنفاق):

| الإعداد | الاستعمال |
| --- | --- |
| `LLM_API_KEY` | مفتاح المزوّد (سرّ) |
| `LLM_MODEL` | اسم النموذج؛ الافتراضي `openrouter/free` |
| `LLM_BASE_URL` | رابط الواجهة؛ الافتراضي `https://openrouter.ai/api/v1` (https فقط) |

للتجربة: نموذج مجاني على OpenRouter (اسمه ينتهي بـ`:free` ويدعم الأدوات) **ببيانات
وهمية فقط**، فمزوّدو المجاني قد يسجّلون الطلبات. وللعميل الحقيقي نموذج مدفوع: يُبدَّل
بتغيير `LLM_MODEL` ثم تشغيل مسار `supabase-deploy`، دون إعادة بناء أي تطبيق. حدود
المجاني 20 طلباً في الدقيقة و50 يومياً (1000 بعد شراء رصيد 10)، وكل استدعاء أداة
يستهلك طلباً.

مسار `supabase-deploy` يضبط هذه الأسرار من Environment المدرسة ويرفع الدوال؛ ويدوياً:

```bash
supabase secrets set LLM_API_KEY=<مفتاح المزوّد> LLM_MODEL=<اسم النموذج>
supabase functions deploy assistant
```

`SUPABASE_URL` ومفاتيح المشروع (`SUPABASE_PUBLISHABLE_KEYS` و`SUPABASE_SECRET_KEYS`)
توفّرها منصة Supabase للدالة. أدوات المساعد مقيَّدة بالدور والجلسة، وأي تغيير يطلبه يظهر
معاينةً وينتظر تأكيداً صريحاً من المستخدم. دون اتصال أو دون إعداد الدالة تعرض الشاشة
أن المساعد غير متاح. اختبارات الدالة: `deno test --allow-env supabase/functions/assistant/index_test.ts`.

على Android يملأ الإملاء الصوتي مسودة قابلة للتعديل ولا يُرسل الكلام حتى يضغط المستخدم
«إرسال»، وتقرأ الإجابة صوتياً بمحرك Android؛ Windows نصي فقط.

## 6. النسخ الاحتياطي والتصدير على Google Drive

تطبيق الإدارة يرفع إلى Drive حساب صاحب المدرسة وحده (نطاق `drive.file` فقط): نسخة
احتياطية يومية من القاعدة (يحتفظ Drive بآخر 30 منها) وملفات التصدير (مثل كشف الحضور
بصيغة Excel) في مسارات مرتَّبة بالفئة. تنشأ نسخة اليوم عند بدء الإدارة وتُراجَع كل ساعة أثناء فتح التطبيق.

متغيرات البناء (انظر `.github/workflows/build.yml`):

| المتغير | الاستعمال |
| --- | --- |
| `GOOGLE_DRIVE_OWNER_EMAIL` (اختياري) | بريد افتراضي لبناء خاص بمدرسة فقط؛ في النسخة العامة يضبطه المالك على جهازه |
| `GOOGLE_DRIVE_WINDOWS_CLIENT_ID` و`GOOGLE_DRIVE_WINDOWS_CLIENT_SECRET` | عميل OAuth لنسخة Windows (تدفق desktop PKCE) |

يحتاج Android عميل OAuth من نوع Android في Google Cloud بصمةُ SHA-1 لمفتاح توقيع
التطبيق (المهمة 8.4). في CI تُحفظ الأسرار في **Settings ← Secrets and variables ←
Actions**: `GOOGLE_DESKTOP_CLIENT_SECRET` سرّ، و`GOOGLE_DRIVE_WINDOWS_CLIENT_ID` و
`GOOGLE_SERVER_CLIENT_ID` (عميل Web) متغيّران عامّان.

بريد المالك لا يُضمَّن في الملف العلني: يضبطه صاحب المدرسة من شاشة Drive (زر «ضبط البريد») على كل
جهاز، ويُحفظ محلياً في جدول `device_info` غير المتزامن (فلا يراه المعلمون ولا الأولياء، ويبقى عند
استعادة نسخة احتياطية). ورموز ربط Windows في التخزين الآمن بمفتاح خاص بكل مدرسة.

## 7. إشعارات الدفع (Firebase)

الإشعارات اللحظية داخل التطبيق تعمل عبر Realtime. إشعارات الدفع (والتطبيق مغلق) تمرّ بالخادم:
مشغّلان في قاعدة المدرسة على `notifications` و`chat_messages` يستدعيان دالة `send-push` التي ترسل
عبر FCM HTTP v1 إلى معرّفات تثبيت Firebase المسجَّلة للمستلمين، والإشعار الذي يصل (من النوع `chat` أو
`notification`) يفتح شاشته. مشروع Firebase واحد للمطوّر يخدم كل المدارس، وقيمه أسرار على مستوى المستودع:

| الاسم | النوع | محتواه |
| --- | --- | --- |
| `GOOGLE_SERVICES_JSON` | سرّ | ملف `google-services.json` الواحد بعد تسجيل التطبيقات الثلاثة `dz.school.admin` و`dz.school.teacher` و`dz.school.student`؛ أو لكل تطبيق سرّ `GOOGLE_SERVICES_ADMIN` و`GOOGLE_SERVICES_TEACHER` و`GOOGLE_SERVICES_STUDENT` |
| `FIREBASE_SERVICE_ACCOUNT` | سرّ | مفتاح حساب الخدمة (Project settings ← Service accounts ← Generate new private key) |

يضع مسار `build` الملف في `apps/<التطبيق>/android/app/google-services.json` ويفعّل
`--dart-define=FIREBASE_PUSH_ENABLED=true`، فتُطبَّق إضافة `com.google.gms.google-services` (دون الملف لا
تُطبَّق ويبقى التطبيق بلا دفع). ويضبط مسار `supabase-deploy` لكل مدرسة سرّ الدالة
`FIREBASE_SERVICE_ACCOUNT` وسراً مشتركاً جديداً `PUSH_SECRET` في كل نشر. مهمة `android-firebase` في `check`
تبني التطبيقات الثلاثة بملف اصطناعي لإثبات توافق الإضافة مع إصدار Android Gradle Plugin. فحص `preflight`
يتحقق من صيغ هذه الأسرار دون طباعتها.

## 8. الرسائل القصيرة وصلاحياتها (Android)

الرسائل تُرسل **من هاتف الإدارة نفسه** بشريحته (لا خدمة وسيطة): تطبيق الإدارة على
Android يفرغ طابور `sms_queue` برسالة كل 3 ثوانٍ. الإرسال الفعلي من Android وحده (منصة
الإرسال تستعمل `SmsManager`)؛ ما يُضاف إلى الطابور من أي جهاز يُرسَل حين يفرغه هاتف الإدارة.

- الصلاحيات في `AndroidManifest.xml`: `SEND_SMS` و`READ_PHONE_STATE` (تعرّف الشرائح)
  و`FOREGROUND_SERVICE` و`FOREGROUND_SERVICE_SPECIAL_USE` و`POST_NOTIFICATIONS`. تُطلب
  `SEND_SMS` و`READ_PHONE_STATE` وقت التشغيل من شاشة الرسائل عند أول إرسال.
- **الهاتف بشريحتين** لا يرسل حتى تُختار الشريحة من إعدادات الرسائل (تُحفظ خانتها لا
  معرّف اشتراكها المؤقت). شريحة واحدة تُختار تلقائياً.
- ساعات الهدوء: الرسائل بين 21:00 و07:00 تُؤجَّل إلى 07:00. وللحد الشهري خيار في
  الإعدادات (صفر بلا حد).
- الفشل المؤقت يُعاد بمهل متزايدة (دقيقة ثم 5 ثم 15 ثم 60) ثم يُعلَّم فاشلاً بعد 5
  محاولات؛ ويمكن إعادة محاولة الفاشل يدوياً. رسائل إنشاء الحسابات وكلمات السر تُمسح
  كلمة السر منها بعد الإرسال.
- المرسل يعمل بخدمة مرئية في المقدمة أثناء التفريغ، فيظهر إشعار حتى ينتهي.
- قوالب الرسائل تُعدَّل من شاشة الرسائل بمتغيرات مثل `{name}` و`{school}`.

## 9. بناء كل تطبيق

```bash
# Android: apk لكل تطبيق
cd apps/admin   && flutter build apk --release    # + --dart-define لـ SUPABASE_* و GOOGLE_DRIVE_OWNER_EMAIL
cd apps/teacher && flutter build apk --release
cd apps/student && flutter build apk --release

# Windows (نسخة الإدارة)
cd apps/admin && flutter build windows --release

# iPhone (على macOS بـXcode 26 فقط؛ في CI مسار ios): .app غير موقَّع يُضغط في Payload/ ليصير .ipa
cd apps/student && flutter build ios --release --no-codesign
```

نسخ iPhone لا تحتاج Mac عندنا: يبنيها مسار `ios` على خوادم GitHub، وتثبيتها مجاناً من Windows في `IOS.md`.

التوقيع: يقرأ Gradle المفتاح من متغيرات البيئة `SCHOOL_KEYSTORE_PATH` و
`SCHOOL_KEYSTORE_PASSWORD` و`SCHOOL_KEY_ALIAS` و`SCHOOL_KEY_PASSWORD`؛ فإن لم توجد وُقّع
الإصدار بمفتاح النسخ التجريبية `tool/signing/preview.jks` (غير سرّي، للنسخ التجريبية فقط).
**مفتاح التوقيع النهائي سرّ** يُحفظ في أسرار GitHub (`SCHOOL_KEYSTORE_BASE64` وكلمتا
السر والاسم المستعار) ولا يدخل المستودع.

### تثبيت تطبيق الإدارة على Windows (جهاز آخر)

الأسهل: **`school-admin-setup.exe`** من صفحة Releases (Windows 10 وما بعده، 64 بت). يُثبَّت لمستخدم واحد دون صلاحيات
مدير، وينشئ اختصاراً في قائمة ابدأ (وعلى سطح المكتب إن اخترته)، ويُزال من «Apps & features». الملف غير موقَّع، فقد
تعرض Windows تحذير **SmartScreen**: اختر «More info» ثم «Run anyway». النسخة المحمولة `school-admin-windows.zip` تضمّ
الملفات نفسها لمن لا يريد تثبيتاً.

**لا تظهر رسائل DLL على جهاز نظيف:** مكتبات Visual C++ (`vcruntime140.dll` و`msvcp140.dll` و`vcruntime140_1.dll`...) لا
تأتي مع Windows، وكانت تظهر عند تشغيل `admin.exe` على جهاز لم يثبّت Visual C++ Redistributable. يضمّها المسار الآن بجانب
`admin.exe` (نشر محلي للتطبيق)، ويتحقق **`tool/windows_dll_check.py`** من جدول الاستيراد في كل `.exe` و`.dll` أن كل مكتبة
مطلوبة مجمَّعة أو من Windows نفسه (وإلا فشل البناء)، ثم يثبّت المثبّت صامتاً ويشغّل التطبيق ويزيله. الاستثناء المعروف
`dartjni.dll` (جسر JNI تجلبه مكتبات Android ولا يُحمَّل على Windows). ملاحظة: إصدارات Windows N تحتاج «Media Feature
Pack» لتعمل الكاميرا.

تثبيت الـAPK من الهاتف: نزّله من صفحة **Releases** في GitHub ثم افتحه، وفعّل «تثبيت
تطبيقات من مصادر غير معروفة» لمتصفح التنزيل إن طُلب.

### ربط الجهاز بمدرسة وقت التشغيل

**مع دليل المدارس لا يوجد رمز ربط:** بناء Releases يضمّن عنوان الدليل (`DIRECTORY_URL` و`DIRECTORY_KEY` عبر `--dart-define`)، فيدخل صاحب المدرسة
والعمال في تطبيق الإدارة برقم الهاتف وكلمة السر (تُسجَّل أرقامهم في الدليل مجزّأة عند إنشاء الحساب)، ويعرض تطبيقا الأستاذ والوليّ قائمة المدارس
لاختيار مدرستهما قبل الدخول؛ ويغيّر صاحب المدرسة والعمال رقمهم وكلمة سرهم من «حسابي». الفقرة التالية تخص البناء دون دليل.

النسخة المنشورة في Releases **عامة**: لا تضمّن خادم أي مدرسة، فملف واحد يخدم كل المدارس. عند أول
تشغيل يطلب التطبيق «رمز المدرسة» (يبدأ بـ`SCH1.`) لصقاً أو مسحاً بالكاميرا ويحفظه على الجهاز. لكل
مدرسة قاعدة محلية وصور خاصة بها، فلا تختلط بيانات مدرستين على جهاز واحد. تغيير المدرسة من شاشة الحساب
← «تغيير المدرسة».

- الرمز يحمل عنوان خادم المدرسة ومفتاحه **العام** واسمها (لا سرّ فيه)، ويرفض التطبيق أي رمز يحوي مفتاحاً
  سرّياً. يعرضه تطبيق الإدارة نصاً وQR من الحساب ← «رمز ربط الأجهزة الأخرى».
- لأول جهاز (قبل أن يوجد تطبيق إدارة مرتبط): `python3 tool/pairing_code.py --ref <معرّف مشروع Supabase>`
  (يلزم `SUPABASE_ACCESS_TOKEN` في البيئة)، أو `--url` و`--key` و`--name`.
- بناء خاص بمدرسة يضمّن إعدادها فيتخطى شاشة الربط: شغّل مسار `build` يدوياً بمدخل `school`.
- تطبيق الإدارة يعمل «معاينة محلية» بلا خادم من شاشة الربط نفسها.

### التحديث التلقائي للتطبيقات

كل تطبيق من النسخة العامة يفحص آخر إصدار في GitHub (التجريبية منها أيضاً) بعد تشغيله بـ20 ثانية ثم كل 6 ساعات،
فإن وجد إصداراً أحدث من `APP_RELEASE` الذي بُني به **نزّل ملفه في الخلفية** (أندرويد: `school-<التطبيق>.apk`، وWindows:
`school-admin-setup.exe`) وتحقق من حجمه وبصمة SHA-256 التي يعلنها GitHub، ثم يعرض شريطاً **«نسخة جديدة جاهزة للتثبيت»**
أعلى الشاشة بزر «تثبيت الآن». من شاشة الحساب ← «التحديث» يُرى الإصدار الحالي ويُفحص يدوياً.

- **أندرويد:** يفتح الزر نافذة تثبيت النظام للموافقة (لا يسمح أندرويد بتثبيت صامت خارج المتجر)، وعند أول مرة يطلب
  النظام السماح للتطبيق بالتثبيت من هذا المصدر (`REQUEST_INSTALL_PACKAGES`). تبقى البيانات والربط، شرط التوقيع بالمفتاح
  نفسه (لذلك `preview-6` وما بعده فقط؛ النسخ الأقدم بمفتاح تجريبي تُحذف قبل تثبيته).
- **Windows:** يشغّل المثبّت صامتاً (`/VERYSILENT /CLOSEAPPLICATIONS /relaunch=1`) ثم يغلق التطبيق نفسه فيُثبَّت فوق النسخة
  القديمة ويُعاد فتحه، دون صلاحيات مدير ما دام التثبيت الأول لمستخدم واحد.
- **شبكة بيانات الهاتف:** لا ينزّل تلقائياً إلا على Wi‑Fi أو كابل؛ على بيانات الهاتف يعرض «نسخة جديدة متاحة (حجمها N ميغابايت)»
  ببطاقة «تنزيل» و«لاحقاً» حتى لا تُستهلك الباقة دون موافقة.
- **متى يُعطَّل:** بناء التطوير وبناء مدرسة خاص (مدخل `school`) بلا `APP_RELEASE`، فلا يستبدل جهازٌ بناءَه بنسخة عامة. ويقرأ
  مستودعاً عاماً فقط (`UPDATE_REPO` = مستودع المسار)؛ إن صار خاصاً تلزم قناة تحديث أخرى.
- **أمان:** لا يقبل التطبيق إلا ملفاً من `github.com/<المستودع>/releases/download/` وبصمته معلنة، ويرفض التالف. ثقته بحساب GitHub
  لمالك المستودع فحمايته (التحقق بخطوتين) جزء من الأمان؛ مثبّت Windows غير موقَّع.
- يتحقق مسار `build` بعد النشر (`tool/release_check.py`) أن كل ملف موجود ببصمة ورابط سليمين، وإلا فشل فلا يصل أجهزةً إصدار لا
  يستطيع تحديث نفسه. أول إصدار فيه المحدِّث `preview-7`؛ `preview-6` وما قبله يُحدَّث يدوياً مرة واحدة.

### مسارات GitHub Actions

| المسار | متى يعمل | ماذا يفعل |
| --- | --- | --- |
| `check` | كل push وطلب دمج | التنسيق والتحليل الصارم ودالة المساعد وكل الاختبارات، ومهمة `server-sql` لاختبارات الخادم |
| `build` | تغيّر محتوى `RELEASE_VERSION` أو يدوياً | يبني ثلاثة APK ومثبّت Windows ونسخته المحمولة **عامة** (بلا إعداد مدرسة) وينشرها في GitHub Releases باسم النسخة؛ ويدوياً مع مدخل `school` يبني نسخة تلك المدرسة أرتيفاكتاً فقط |
| `windows-installer` | تغيّر ملفات المثبّت أو يدوياً | يبني مثبّت Windows ويتحقق منه (نسخ مكتبات Visual C++، وفحص اكتمال المكتبات، وتثبيت صامت وتشغيل وإزالة) **دون نشر**؛ المثبّت أرتيفاكت أسبوعين |
| `ios` | يستدعيه `build`، أو عند تغيير ملفات iOS، أو يدوياً | على macOS-26: يشغّل كل تطبيق على محاكي iPhone حتى شاشته الأولى ثم يبني `.ipa` غير موقَّع ويفحصه (`tool/ipa_check.py`)؛ انظر `IOS.md` |
| `perf` | يدوياً أو عند تغيير اختبار القياس | قياس زمن الإطارات على محاكي Android (انظر `PERFORMANCE.md`) |
| `release-smoke` | يدوياً أو عند تغيير ملفاته | يفحص إصداراً منشوراً دون أجهزة: يثبّت التطبيقات الثلاثة على محاكي Android ويشغّلها ويقارن بصماتها بما يعلنه GitHub، ويشغّل المحدِّث الحقيقي على الإصدار؛ ومسار `build` يستعمل الإجراء نفسه بوابةً قبل النشر |

إصدار نسخة: غيّر محتوى `RELEASE_VERSION` (مثل `preview-5`) وادفع، وتحقق من نجاح `build`.

## 10. الجودة والأداء

- المنطق الحسابي كله في `packages/core` مرة واحدة ولا يتكرر في التطبيقات.
- كل كتابة في جدول مزامَن تمر عبر `SyncWriter` (حفظ + سجل عمليات + طابور مزامنة في
  معاملة واحدة)، والسجلات ذات المفتاح الطبيعي تأخذ معرّفها من `StableId`.
- اختبارات التكامل: `packages/core/test/integration` (تسجيل ← مسح ← دفع ← اكتمال دورة ←
  خلاص) و`packages/sms/test/integration` (طلب أستاذ ← موافقة ← SMS).
- مولّد بيانات الأداء (2000 تلميذ و100 فوج وسنة حضور و50 ألف رسالة):
  `PerfDataGenerator` في `package:school_core/testing.dart`.
- قياسات الاستعلامات والماسح وزمن الإطارات وميزانياتها وما أُصلح بها: **`PERFORMANCE.md`**
  (تمييز صريح بين أرقام حاسوب التطوير والمحاكي وهاتف حقيقي).

## 11. ملفات المتابعة

`PLAN.md` الخطة، `PROGRESS.md` حالة كل مهمة، `ANSWERS.md` المواصفات المعتمدة،
`DECISIONS.md` كل قرار وسببه، `DONE.md` ملخص الإنجاز وروابط التحميل والتثبيت وما لم يُجرَّب بعد، `QUESTIONS.md` الأسئلة والبيانات المؤجَّلة،
`OPERATIONS.md` تشغيل المدارس (إضافة مدرسة والكلفة والأمان)، `PRIVACY.md` سياسة الخصوصية (تُربط من شاشة موافقة
Google)، `PERFORMANCE.md` الأداء، `HANDOFF.md` و`LOCAL_PROMPT.md` للتناوب بين أدوات العمل.
